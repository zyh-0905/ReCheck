## 2. 必须进一步收紧的一项解释

R10先前报告指出8个旧目标提案被拒绝。这个事实可核对，但**不能省略其中的条件字段，再自动称作8次模型错误**。

例如完整动作的含义可以是：

> 仅当服务仍指向配置A时，将A的max_attempts改为5；否则不写入，返回冲突。

当服务已改指B时，按这个API契约返回冲突可能就是合法的乐观并发流程。完整动作可写为`a=(业务修改m, 提交前提p)`。删除p后执行m，是研究者主动改变动作的事后分析，不是模型实际做过的动作。

因此这次采用三个分别记录的判断：

1. 原条件请求是否符合API结构与授权契约。
2. 去掉部分条件后，业务部分在记录的前态会造成什么后果。
3. 原执行器拒绝或接受之后，真实模型最终是否完成任务。

第2项不等于第1或第3项。原R10仍是48/48安全完成、没有实际错误写入；不能追溯改成40/48，也不能把8/48称作模型或生产事故发生率。它们只表明部分业务载荷依赖选择条件的保护。

## 3. 首次提案的完整对照

每行对同一48个首提案做一次单步重放：

| 保留的原有前提 | 合规提交 | 不合规提交 | 拒绝本可合规的业务补丁 | 拒绝会不合规的业务补丁 |
|---|---:|---:|---:|---:|
| 不保留可选前提 | 40 | 8 | 0 | 0 |
| 仅行版本 | 26 | 8 | 14 | 0 |
| 仅选择条件 | 40 | 0 | 0 | 8 |
| 全部原有前提 | 26 | 0 | 14 | 8 |

“仅保留”不代表每个请求都获得这一前提；原请求没有就仍然没有。模式名称不能被解释成重新设计的新算法。

原执行器第一次接受26个，拒绝22个，模型处理可见冲突后最终全部48个成功。8个对选择条件敏感的载荷来自x03路由和x09排名两种情形的四个提示组，不能膨胀成8类独立任务。

14个保守拒绝来自owner/carrier变更。实际最小补丁不覆盖这些字段，选择目标也未变化，因而在本任务规范及记录前态下仍可合规。这个结论不支持实际部署中普遍取消行版本检查；附加不变量、并发写入和其他业务规范没有被本检查覆盖。

| 无 | 62 | 8 | 0 | 0 |
| 仅行版本 | 48 | 8 | 14 | 0 |
| 仅选择 | 62 | 0 | 0 | 8 |
| 全部 | 48 | 0 | 14 | 8 |

48个首提案×4＝192次转移，22个后续提案×4＝88次转移，合计**280次原生SQLite转移**。其中70个“全部原有前提”分支逐字复现原工具结果与后态。

后续22个提案是原守卫拒绝后，模型重新查询产生的。无守卫系统可能根本不会访问这些后续状态。因此不能把“无前提”一列的62次合规提交串接成一个新Agent成绩，更不能据此计算替代策略的端到端恢复率、延迟或节省的token。

上一轮22个拒绝点的局部检查已在这个全集中，属于覆盖范围扩展和口径细化，不重复当作新增独立证据。
