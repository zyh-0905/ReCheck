## 4. 两类失败到底发生了什么

### 4.1 人物目标：消息读回证明写到了某个号码，不证明写给了目标人物

`primary_n02_inherited`和`primary_n02_verify_confirm`：

1. 事件0，模型实际查询到目标人物ID `9e137f06-916a-5310-8174-cf0b7e9f7054`，号码`+12453344098`。
2. 事件1—2，预定环境更新把此人的号码改为`+12025550129`，并把旧号码分配给ID `a22e1984-6c6c-530c-8831-c3ea3b5138e7`。
3. 事件3，蜂窝查询返回true；这是同一模型响应的第二个工具，不能刷新人物绑定。
4. 下一次模型决策在事件4仍使用旧号码发送。原生工具成功，但新消息的recipient_person_id为另一人。
5. Verify-confirm随后用真实消息ID读回。该回执包含另一人的recipient_person_id；模型最终仍声称发给了原目标且已验证。Inherited没有这次写后消息查询。

**没有截断或伪造工具结果：所有调用与回执都真实执行在模拟数据库。问题是操作结果与目标身份没有重新核对。**不能凭模型reasoning_content推断内部原因，也不把完成声称不实解释为有意欺骗。

### 4.2 提醒目标：完整旧字段写回改变了新内容，随后按旧ID核验

`primary_n10_inherited`和`primary_n10_verify_confirm`：

1. 事件0，描述查询返回旧ID `54f20be9-eac3-5e76-8e57-724e48d3d477`，文本为`Review the indigo rehearsal plan`。
2. 事件1—2，环境把此旧ID文本改成`Inspect the storage locker`，同时把ID `da2b856e-9390-511f-bcbe-7005f72cbf5e`改成用户要求的目标文本。
3. 事件3，模型继续修改旧ID，不仅提交新提醒时间，还显式提交旧content和经纬度。于是错误对象的文本被改回旧目标文本，形成两条同名提醒。
4. 随后按旧ID查询，读到模型刚刚写入的文本和时间，结束语声称“文本未变、没有修改其他提醒”。
5. 真正当前匹配的ID `da2b…`时间仍为1800103600，而非要求的1800118800；同时出现重复描述。因此不仅有过程性误写，最终目标与最终业务状态也不合格。

原评分只忽略上游自动变动的creation_timestamp；content、时间与位置从未被豁免。冗余提交旧字段并非在所有情况下都无害，必须与**实际提交前状态**比较，而不是只与旧查询值比较。

上述四个失败中，3个主回合有实际写后查询，1个没有。不能写成四个都进行了写后核验，也不能写成工具成功等于目标成功。

## 5. 本次研究端追加的零模型调用诊断

所有诊断在副本上进行，不改变原32个主结果，不计为新LLM样本：

- 对四个失败主回合的最终快照，各做一次按当前人物名/提醒文本的原生只读查询。人物查询显示新号码；提醒查询显示两条同名记录，真目标时间仍未更新。四次查询均不改变业务状态。
- 对两个提醒失败，从原始前缀重放到错误修改之前，只保留`reminder_id`和用户要求修改的`reminder_timestamp`再执行。旧ID仍然错误，两个诊断仍不安全；但按ID读回会显示`Inspect the storage locker`，而不是被覆盖回原文本。

这证明了一个局部可观察差别：**省略不必要的旧字段不会自动解决错误ID，但可以避免额外覆盖并保留可供检测的文本冲突。**它不是新模型的恢复结果，不是“修改两行参数就修好了Agent”，也不证明任何核验算法普遍有效。数据见`results/posthoc_observability.json`。

## 6. README三项关键解释修正

### 6.1 本轮确实出现了同一响应多个工具调用

139份响应中：36份自然语言结束、82份单工具、21份双工具。主结果是19份双工具，重复诊断2份。103个tool_calls响应对应124个工具事件。

所以“无单次响应多个动作”不正确。**这些是协议允许、整批校验后顺序执行的结构化调用，与旧文本中夹杂多个JSON动作不是同一问题。**最大2个，小于4个上限。

21个双工具批次全部由读取工具组成：查询联系人+读蜂窝10次，读Wi-Fi+读低电量8次，读蜂窝+读低电量1次，两次提醒查询1次，读低电量+读Wi-Fi1次。没有观察到同一响应中的查询+主要写入。

### 6.2 24个主回合事件不是全部在查询后发生

8个pre_relevant在回合开始前触发；16个post情形在合格查询后触发；另8个stable不安排。所有已安排事件均触发，没有漏暴露。

全体28个触发回合（含4重复）对应44个管理工具操作；44不是44次独立变化。16个post主回合的第一个主要写入均位于**后续模型响应**，不是触发查询所在的同一响应。因此，四次主误写不能归因于“同批工具之间没有模型重选机会”。

Wi-Fi n14中，模型先读Wi-Fi，环境启用低电量，再在同一响应的第二次读取中得到low_battery=true，随后合法关闭它、开启Wi-Fi。实际没有抛出业务异常；这是利用新观测主动满足前置条件，不是异常后的恢复成绩。

### 6.3 四种读法的分歧只有最弱代理指标

本批`goal_final == final_state_clean == trace_safe_success`在32个主回合及4个重复中均成立，最终目标/业务状态接受的全过程误写数为0。

“工具成功代理接受4个失败主回合”成立；但**“只看最终状态会漏掉本批误写”不成立**。原研究希望观察的更强评分差异本轮未出现，必须保留为未确认结果。不能把弱工具指标当成官方评分规则，或事后改成存在性匹配以制造新的主结果。
